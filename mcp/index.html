Shape of the thing

A Cloudflare Worker exposes a remote MCP endpoint at /mcp over streamable HTTP. It holds a D1 binding to the risk database and nothing else. Claude (desktop, or the API with an MCP connector) attaches to it and can then answer questions about the register directly rather than being handed an export.

Claude  ──MCP over HTTP──▶  Worker (/mcp)  ──binding──▶  D1: risk_demo
                                  │
Browser ──static assets───▶  same Worker  ──fetch /api/*──▶ same D1

The web UI and the MCP server sit on the same database and, deliberately, the same query surface — the functions in assets/js/api.js mirror the tool list below one-for-one. If a person can see it in the UI, the assistant can ask for it, and both get the same numbers.

One constraint worth stating early: the D1 binding and a Worker entry point have to be declared in wrangler.toml, which this repository's deployment setup owns. The MCP server therefore ships either as a change to that file made by the repository owner, or as a second Worker with its own configuration. It is not something the site build can add on its own.

Read tools

Phase one — everything the demo needs
ToolArgumentsReturns
list_incidents status, severity, department, system, process, category, owner, occurred_from, occurred_to, search, limit Matching incidents from v_incident_summary, newest first.
get_incident reference (e.g. INC-2026-018) One incident with its actions, the controls that were in scope and how each performed, the systems touched, and the update timeline.
list_actions status, priority, action_type, overdue, owner, department, incident, control Actions from v_action_summary, including the derived overdue flag.
list_controls effectiveness, control_type, automation, department, system, process Controls from v_control_health with failure counts and coverage.
get_control code (e.g. CTL-02) One control with its processes, linked incidents and open actions.
risk_summary period_months (default 12) Counts, loss totals, the monthly series, the likelihood × impact grid and per-department exposure — one call for "how are we doing?".
list_reference entity: departments | systems | processes | people | risk_categories The reference registers, so the assistant can resolve a name to an id before filtering.
search query, limit Cross-entity keyword search over incidents, actions and controls, each hit tagged with its type.

Write tools

Phase two — gated

Writes are where a risk system gets interesting and where it gets dangerous, so they come second and they come with rules:

  • create_incident — raise an event. Returns the allocated reference.
  • add_incident_update — append to the timeline, optionally moving status.
  • create_action — raise a mitigation against an incident and, optionally, a control.
  • update_action_progress — move status and percentage complete.
  • update_control_effectiveness — record a test result.

Every write tool is annotated as non-read-only so the client prompts for confirmation; every write is attributed to the calling identity and lands in incident_updates as an audit trail. Nothing is ever hard-deleted — statuses move to cancelled or closed instead. A demo token scoped to a single seeded database keeps the blast radius at zero.

Questions the demo should answer

  • "What's open and material right now?" — risk_summary then list_incidents filtered to open, high and critical.
  • "Why did the duplicate payment happen, and is it fixed?" — get_incident INC-2026-018 returns the root cause, the control that failed (CTL-02, keyed on file hash alone) and the two actions raised against it.
  • "Which controls keep failing?" — list_controls sorted by failure count surfaces CTL-07, CTL-10 and CTL-13.
  • "What is Payments carrying?" — department filter across incidents and actions in two calls.
  • "Draft the monthly risk report." — one risk_summary plus list_actions(overdue) is enough material for a first draft.

Implementation notes

  • SQL lives in parameterised statements only — tool arguments are never concatenated into a query. The closed enumerations in the schema make argument validation cheap.
  • Every list tool takes limit (default 50, hard cap 200) and returns a total alongside the rows, so a broad question degrades into a summary rather than a context-flooding dump.
  • Results are returned as structured content matching the tool's output schema, with a short text rendering for clients that only read text.
  • Read tools are annotated read-only and idempotent; that is what lets a client run them without prompting.
  • The same Worker serves /api/* for the browser, so there is one place where a query is written and one place where it can be wrong.
