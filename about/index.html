What this is

Most operational risk tooling is a database with forms on top. The data is genuinely useful — incidents, the controls that failed, the actions raised to fix them — and it is almost always trapped behind a reporting cycle. Someone asks "what's our exposure in Payments?" and the answer arrives a week later as a slide.

This demo exists to show the alternative: the same database, with a small MCP server in front of it, so an assistant can answer that question in the conversation where it was asked. The web interface here is the human view of exactly the same data — deliberately so, because a demo where the chat answer and the dashboard disagree is not a demo of anything.

Everything in it is fictional. Meridian Financial Group does not exist. The twenty-two incidents, the people who own them and the losses attached to them were written to be plausible, varied and safe to show to anyone.

What is real today

  • The data model — twelve tables with real foreign keys, check constraints and four views, ready to apply to Cloudflare D1. See Data model.
  • The dataset — 9 departments, 16 people, 12 systems, 13 processes, 14 risk categories, 20 controls, 22 incidents, 37 actions and their join rows, with a generated db/seed.sql.
  • The front end — every screen you can click, running on that dataset: filtering, sorting, the heat map, the trend, the incident records.

What is not built yet

  • The MCP server itself. It is specified down to the tool list and arguments on the MCP server page, but no Worker code is written.
  • The /api routes over D1. The browser reads /assets/data/demo.json; the data access layer is written so that swapping in fetch('/api/incidents') touches one module.
  • Writes. Nothing in this interface edits anything. Adding an incident or closing an action is phase two, and it arrives with an audit trail.

How it is built

Static HTML, CSS and ES modules — no framework, no build step, no dependencies. It is served by a Cloudflare Worker with static assets, deployed from main by GitHub Actions. The whole site is a handful of files:

index.html              dashboard
incidents/              register + detail record
actions/  controls/     the two other registers
registers/              departments, systems, processes, people
data-model/  mcp/  about/

assets/js/api.js        the only module that knows where data comes from
assets/js/ui.js         shell, formatters, status badges, sortable tables
assets/js/charts.js     inline-SVG line, bar, heat map and status meter
assets/data/demo.json   the dataset
db/schema.sql           D1 DDL
db/seed.sql             generated from demo.json

Charts are hand-rolled SVG rather than a charting library: single-series marks use one blue, magnitude uses a one-hue blue ramp, and a reserved four-colour status palette is used only for state — always alongside a text label, never colour on its own. Each chart also offers its underlying numbers as a table.

Light and dark themes are both selected rather than inverted, and the toggle in the header overrides the system preference.

Reading the data

A few conventions worth knowing before you click around:

  • Risk score is likelihood × impact, each scored 1–5. The heat map plots open incidents on that grid; selecting a cell filters the register to it.
  • Severity is the assessed seriousness of the event, independent of the score. Status moves open → under investigation → pending action → closed.
  • Net loss is gross loss less recoveries. Several incidents carry a zero net loss and still matter — a near miss on sanctions screening costs nothing and is reportable.
  • Control effectiveness is the result of the last test. The failures column counts incidents where that control was in scope and did not hold — a control can be rated partially effective and still have failed twice.
  • Today is pinned to the dataset's as_of date, so overdue actions stay overdue and the demo does not drift.
