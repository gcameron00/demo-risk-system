Two further join tables are not drawn to keep the diagram readable: incident_systems (an incident usually touches more systems than its primary one) and control_processes (a control covers many processes, a process is covered by many controls).

The core tables

incidents

An operational risk event that has already happened. Carries the narrative (description, root_cause), the scoring (severity, likelihood, impact), the money (gross_loss, recovery_amount, net_loss) and the foreign keys that say where it happened: department, process, primary system and risk category.

actions

What is being done about it. Each action points back at its incident and, where the fix is a control change, at the control it strengthens. action_type distinguishes one-off remediation from enhance an existing control and stand up a new one.

controls

The mitigations already in place, with an operating effectiveness rating and a design_rating. A control is linked to the incidents it was in scope for through incident_controls, which records how it performed — that is where "which controls keep letting us down" comes from.

The reference tables

departments & users

Departments nest through parent_department_id and name a head. Users belong to a department, report to a manager, and hold a role that a future write API would use for authorisation.

processes & systems

The two lenses on how work gets done. An incident names the process that broke and the system it broke on; a control names the system it runs in and the processes it covers.

risk_categories

A two-level Basel-style event taxonomy — seven level-one categories with level-two children such as Payment & card fraud and Change & release failure.

incident_updates

The timeline: who said what, when, and any status transition. It is what makes an incident readable months later, and it gives an assistant something to summarise.

Views

The shared read surface

Four SQL views exist so the web UI and the MCP server answer the same question the same way, rather than each re-deriving "open", "overdue" or "significant" in its own code:

  • v_incident_summary — incidents with lookups resolved, a derived risk_score and action counts.
  • v_action_summary — actions with their incident and control context and an is_overdue flag computed against date('now').
  • v_control_health — each control with its failure count, open actions and process coverage.
  • v_department_exposure — per-department incident counts and net loss, the shape a management pack needs.

The front end reads a JSON fixture with exactly these field names, so swapping it for the live database is a change to one module (assets/js/api.js) and nothing else.

Loading it into D1

# create the database once
npx wrangler d1 create risk_demo

# apply the schema, then the demo rows
npx wrangler d1 execute risk_demo --file=db/schema.sql --remote
npx wrangler d1 execute risk_demo --file=db/seed.sql   --remote

# sanity check
npx wrangler d1 execute risk_demo --remote \
  --command="SELECT status, COUNT(*) FROM incidents GROUP BY status"

db/seed.sql is generated from assets/data/demo.json by node tools/generate-seed.mjs, so the mock-up and the database cannot drift apart. Edit the JSON, regenerate, reload.
